# Pre-Shift Brief

Every restaurant manager gives a pre-shift speech, and today it's vibes plus
yesterday's complaints. **This auto-writes it from live data.**

At 4pm it pulls tonight's reservation book, the weather, the 86 list, and guest
history — figures out who's a first-timer off Google vs. a regular, which regular's
last visit ran long and needs white-glove, and tonight's upsell push — then hands the
manager a **90-second brief** on a web dashboard and by email. Zero new hardware. It
runs off data the restaurant already has.

## How it works

```
Providers (seed | Toast | weather)
        ↓  normalized data model  (src/lib/types.ts)
assembleContext()  →  derived signals  (first-timers, white-glove, pacing, 86, weather)
        ↓
generateBrief()  →  Claude API  →  { narrative, hitList, whiteGlove, eightySix, upsellLine }
        ↓                              ↓
   Web dashboard ( / )          Email (Resend), sent by the 4pm Vercel cron
```

The core idea is a **provider-adapter pattern**: all brief logic and the Claude prompt
read from one normalized data model, so the **seed provider** (built-in, no credentials)
and the **Toast provider** (live, needs partner creds) are interchangeable — nothing
downstream changes when you flip `DATA_PROVIDER`.

## Quick start

```bash
npm install
cp .env.example .env.local        # add ANTHROPIC_API_KEY for the AI narrative

# See the whole data pipeline with zero keys (providers + derived signals):
npm run brief -- --no-ai

# Full brief, generated by Claude (needs ANTHROPIC_API_KEY):
npm run brief

# Web dashboard:
npm run dev                       # http://localhost:3000
```

The dashboard always renders the data cards; if `ANTHROPIC_API_KEY` is missing it
degrades gracefully to data-only with a notice, rather than a blank page.

## Configuration

Non-secret settings (tonight's upsell push, service window, the white-glove ticket
threshold) live in **`config/brief.config.ts`**. Secrets live in `.env.local` — see
`.env.example`. Nothing is required to run the seed pipeline except `ANTHROPIC_API_KEY`
for the narrative.

| Concern | Env |
| --- | --- |
| Claude | `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL` (default `claude-sonnet-4-6`) |
| Data provider | `DATA_PROVIDER` = `seed` (default) \| `toast` |
| Toast | `TOAST_API_HOSTNAME`, `TOAST_CLIENT_ID`, `TOAST_CLIENT_SECRET`, `TOAST_RESTAURANT_GUID` |
| Weather | `WEATHER_PROVIDER` = `nws` (free, default) \| `openweather`; `WEATHER_LAT/LON` |
| Email | `RESEND_API_KEY`, `EMAIL_FROM`, `BRIEF_RECIPIENTS` |
| Cron | `CRON_SECRET` (required — cron fails closed without it) |
| Dashboard auth | `DASHBOARD_USER`, `DASHBOARD_PASSWORD` (set both to require login) |

## Access control

The dashboard and brief APIs expose guest PII (names, allergies, spend, visit
history) and bill Claude on demand, so they're gated by **HTTP Basic auth**
(`src/middleware.ts`): set `DASHBOARD_USER` + `DASHBOARD_PASSWORD` and every route
requires those credentials. If they're unset the app stays open (so an initial demo
keeps working) — **set them in production.** The cron route is excluded from Basic
auth and instead authenticates with `CRON_SECRET` (which it now requires, failing
closed with a 503 if unset).

## Data & privacy

The brief is built from guest PII — names, allergies, lifetime spend, visit
history — and that context is **sent to the Claude API** (Anthropic) on every
generation to write the narrative. Two things follow from that:

- **PII leaves your infrastructure.** Anthropic processes the prompt under its
  API terms; review them against your guest-data obligations before pointing
  this at a live res book. If a guest's data can't go to a third-party LLM,
  don't include that guest's fields in the context (or run the pipeline with
  `--no-ai`, which renders the data cards without calling Claude).
- **Untrusted text is treated as data, not instructions.** Guest names, notes,
  tags, allergies and 86 reasons are sanitized before they reach the prompt
  (`src/lib/brief/sanitize.ts`): control/zero-width characters are stripped,
  newlines collapsed, and known prompt-injection markers (role delimiters,
  "ignore previous instructions", etc.) neutralized. The system prompt also
  instructs the model to treat the supplied data as untrusted content. This
  reduces — but does not eliminate — indirect prompt-injection risk; the model
  output is still rendered to managers, never executed.

## Integrations

- **Seed** (`src/lib/providers/seed/`) — a realistic, hand-built res book that exercises
  every signal. Default in dev and CI; needs no credentials.
- **Toast** (`src/lib/providers/toast/`) — live reservations, guest CRM, 86 list (menu
  availability) and ticket times (Orders), mapped to the same interface. Machine-client
  OAuth. **Note:** exact Toast endpoint shapes should be verified against current Toast
  partner docs / the sandbox; the client isolates auth + transport so each method is
  independently verifiable.
- **Weather** — National Weather Service (US, free, no key) or OpenWeather. Non-critical:
  any failure degrades to a neutral placeholder.

## Delivery

- **Dashboard** — `/` renders tonight's brief; `?date=YYYY-MM-DD` for another night.
  A **Regenerate** button forces a fresh generation.
- **Email** — `GET /api/cron/send-brief` generates and emails the brief via Resend,
  protected by `CRON_SECRET`. **`vercel.json`** schedules it daily at `20:00 UTC`
  (≈ 4pm US Eastern in summer — adjust the cron for your timezone; Vercel crons run in UTC).

## Tests

`npm test` covers the intelligence layer: first-timer detection, the white-glove
threshold (incl. the 22-min regular case), pacing/peak, headline stats, the seed
provider, and tolerant parsing of Claude's JSON. The Claude SDK is not called in tests.
